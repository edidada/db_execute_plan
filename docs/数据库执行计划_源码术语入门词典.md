# 数据库执行计划与 MySQL 源码术语入门词典

**适合读者**：只做过 CRUD（增删改查）业务开发、会写 SQL，但尚未系统学习数据库内核的 Java/C/C++/后端工程师。  
**范围**：基于所提供的《MySQL 复杂查询的计划生成与执行：源码讲解及日志验证计划》以及本次对话中关于执行计划的讲解与评审。  
**版本背景**：原文固定 MySQL 8.4.6、提交 `3f821bcb4ee93cd90c0ffa0f8e17bb9677502acf`；函数与行号需以该版本核对。  
**阅读建议**：先读“十分钟主线”，再按模块查词。文中“通俗解释”是教学类比，不代表 MySQL 的严格内部类型定义。

## 一、十分钟读懂：从 CRUD 到数据库内核

业务开发通常只需要写：

```sql
SELECT u.name, SUM(o.amount) AS total
FROM users u JOIN orders o ON u.id = o.user_id
WHERE u.age > 25
GROUP BY u.id, u.name
ORDER BY total DESC LIMIT 10;
```

但数据库内部还要解决：**这段 SQL 合法吗？先读哪张表？用哪个索引？怎样 JOIN？怎样分组排序？如何把结果返回客户端？**

```text
SQL 文本
  → Parser（解析器）：看懂语法
  → Resolver / Prepare（语义解析与准备）：确认表、列和表达式
  → Optimizer（优化器）：评估候选方案，选择执行方式
  → AccessPath（访问路径树）：描述选定的物理操作
  → RowIterator（行迭代器树）：构造可运行的算子对象
  → Executor（执行器）：根节点 Init / Read，向下拉取数据
  → handler API（存储引擎接口）→ InnoDB（实际查找记录）
  → Result（结果返回客户端）
```

**最关键的三个区别**：SQL 是“想要什么”，执行计划是“打算怎么取”，执行器是“真正动手取”；估算成本不是实际毫秒；`EXPLAIN` 展示计划不等于完整展示优化器的所有决策过程。

## 二、业务 SQL 与关系运算基础

### 01. CRUD — Create, Read, Update, Delete（增删改查）
业务开发最常见的四类数据操作。对应 SQL 通常是 INSERT、SELECT、UPDATE、DELETE。**例子**：`SELECT * FROM users WHERE id=1` 是 Read。

### 02. SQL — Structured Query Language（结构化查询语言）
向关系型数据库描述数据查询或修改意图的语言。SQL 通常是声明式语言：你说要什么结果，不必逐步指定怎样扫描磁盘。

### 03. Query（查询）/ Statement（语句）
Query 常指查询任务，Statement 指一条 SQL 语句；并非所有 Statement 都是 SELECT。**例子**：`UPDATE users SET age=30` 是语句，但不属于普通 SELECT 查询。

### 04. DML — Data Manipulation Language（数据操纵语言）
操作表中数据的语句类别，通常包括 SELECT、INSERT、UPDATE、DELETE（不同教材对 SELECT 的分类略有差异）。源码类名 `Sql_cmd_dml` 不宜直接理解成“只处理修改”。

### 05. SELECT / WHERE / GROUP BY / HAVING / ORDER BY / LIMIT
SELECT 选输出字段；WHERE 在分组前过滤；GROUP BY 分组；HAVING 过滤分组结果；ORDER BY 排序；LIMIT 限制返回行数。**注意**：SQL 的书写顺序不等于执行器逐句执行的顺序。

### 06. JOIN（连接）
根据关联条件把多张表的记录组合起来。**例子**：`users.id = orders.user_id`。数据库必须决定连接顺序与连接算法。

### 07. INNER JOIN / OUTER JOIN（内连接 / 外连接）
内连接只返回满足关联条件的组合；外连接还要保留指定一侧没有匹配的行，因此某些 JOIN 重排或过滤下推不合法。

### 08. SEMIJOIN / ANTIJOIN（半连接 / 反连接）
半连接关心“是否存在匹配”，通常不把右侧所有匹配行逐个输出；反连接关心“不存在匹配”。与 EXISTS / NOT EXISTS 等查询优化相关。

### 09. Subquery（子查询）
SQL 内嵌的另一条查询。**例子**：`WHERE id IN (SELECT user_id FROM orders)`。优化器可能把它转换成 JOIN、半连接或物化结果。

### 10. CTE — Common Table Expression（公共表表达式）
`WITH t AS (...) SELECT ... FROM t` 定义可引用的临时命名查询结果。是否合并或物化由数据库规则与计划决定。

### 11. Derived Table（派生表）
FROM 中的子查询结果。**例子**：`FROM (SELECT ... ) t`。不等于数据库一定先创建一张物理临时表。

### 12. Aggregate（聚合）/ Aggregation（聚合计算）
把多行合成统计值，例如 COUNT、SUM、AVG；可以对整张表或每个分组计算。

### 13. Predicate（谓词）/ Filter（过滤）
产生真/假/未知判断的条件及其筛选操作。**例子**：`age > 25` 是谓词；Filter 算子按条件过滤记录。

### 14. Projection（投影）
只保留查询需要的列。**例子**：`SELECT name` 不必把 `age` 等所有列都输出。和图形学“投影”不是一回事。

## 三、解析、语义准备和计划生成

### 15. Parser（解析器）
把 SQL 文本解析成语法结构的组件。能识别 `SELECT ... FROM ...` 是否符合语法，但不负责选最便宜的索引。

### 16. Lexical Analysis（词法分析）
把字符流识别为关键字、标识符、数字、符号等记号。**例子**：识别 `SELECT`、`users`、`>`。

### 17. Syntax Analysis（语法分析）
按 SQL 语法规则组织词法记号。**例子**：`SELECT FROM users` 会触发语法错误。

### 18. AST — Abstract Syntax Tree（抽象语法树）
SQL 的语法结构树。它说明写了哪些表达式、表和子句；**AST 不是物理执行计划**。

### 19. Semantic Analysis（语义分析）
检查 SQL 在数据库对象与类型层面是否有意义。**例子**：查询不存在的 `salary` 列会失败。

### 20. Name Resolution / Binding（名称解析 / 绑定）
把 `u.age` 绑定到具体表别名 `u` 所对应的字段，处理同名字段歧义。

### 21. Prepare / Preparation（查询准备）
执行前处理查询结构、字段解析、表达式、权限相关检查及部分变换。MySQL 中多个准备函数协作完成，不是单独一个纯“语义检查”函数。

### 22. Query Block（查询块）
通常指一个 SELECT 查询单元。外层 SELECT 与子查询可能各自形成查询块；MySQL 源码类型 `Query_block`。

### 23. Query Expression（查询表达式）
可包含一个或多个查询块及 UNION 等组合结构的查询表达式；MySQL 源码类型 `Query_expression`。它不等于单个 Query Block。

### 24. Query Rewrite（查询重写）
把 SQL 变换成语义等价、可能更好优化的形式。**例子**：满足条件时合并派生表、改写子查询。

### 25. Logical Plan（逻辑执行计划）
描述扫描、过滤、投影、连接、聚合等逻辑操作，重点是“做什么”；并不完整指定索引和物理 JOIN 算法。

### 26. Physical Plan（物理执行计划）
指定具体实现，如全表扫描、索引查找、Nested Loop Join、排序、临时表等，重点是“怎么做”。

### 27. Operator / Plan Node（算子 / 计划节点）
执行计划树上的一个操作单元，例如 Scan、Filter、Sort。**父子关系**表示数据如何在操作间流动。

### 28. Plan Tree（执行计划树）
由多个计划节点构成的树。父节点通常向子节点索取输入，再处理后向上返回结果。

### 29. AccessPath（访问路径；MySQL 内部计划结构）
MySQL 8.4 中描述所选访问与上层物理操作的结构，可组成树；不应仅理解为“某个索引”。**关键区别**：AccessPath 是计划描述，不是最终执行对象。

### 30. RowIterator（行迭代器）
MySQL 执行器中能初始化并读取行的具体对象；可由 AccessPath 生成。**关键区别**：RowIterator 负责实际运行。

### 31. `CreateIteratorFromAccessPath()`（从访问路径创建迭代器）
MySQL 重要源码函数，把 AccessPath 节点转换为相应的 RowIterator，形成可执行算子结构。适合打断点理解“计划如何落地”。

## 四、优化器、统计信息与成本

### 32. Optimizer / Query Optimizer（查询优化器）
为同一 SQL 比较可行执行方式并选择方案的组件。其选择通常是**估计成本较低**，不保证真实运行时间全球最优。

### 33. RBO — Rule-Based Optimization（基于规则的优化）
按照预定义规则做等价变换。**例子**：条件允许时把过滤下推到扫描附近。

### 34. CBO — Cost-Based Optimization（基于成本的优化）
估算候选方案需要的资源，选择预估更便宜的方案。**例子**：比较全表扫描与索引扫描。

### 35. Statistics（统计信息）
优化器掌握的表行数、索引分布、列值分布等摘要。不是完整业务数据，也可能过期。

### 36. Cardinality（基数 / 行数估计）
语境要区分：可能指集合不同值数量，也可能指某计划节点估算输出行数。阅读优化器源码时应看变量的具体含义。

### 37. NDV — Number of Distinct Values（不同值数量）
一列有多少种不同取值。**例子**：100 万行的 `age` 列只有 80 种年龄，NDV≈80。

### 38. Histogram（直方图）
按区间或值记录数据分布的统计结构，帮助优化器识别数据倾斜，而非一律假设均匀分布。

### 39. Selectivity（选择率）
满足过滤条件的比例。**例子**：100 万行中 1 万行满足 `age=30`，选择率约 1%。

### 40. Estimated Rows / Actual Rows（估算行数 / 实际行数）
前者是优化器预估；后者是执行后观察。两者偏差大时，可能导致选错索引或 JOIN 顺序。

### 41. Cost Model（成本模型）
用内部成本单位估算扫描、CPU、随机访问等代价。**重要**：`cost=100` 通常不表示 100 毫秒。

### 42. Candidate Plan（候选计划）
优化器考虑过的可行方案，例如“先读 users 再读 orders”和反过来的顺序。

### 43. Access Path Selection（访问路径选择）
在扫描表、按索引定位、范围扫描等方式中选择。与 AccessPath 结构相关，但不是完全同一个术语层次。

### 44. Join Order（连接顺序）
多表 JOIN 时先组合哪些表。顺序影响中间结果规模、索引利用和整体成本。

### 45. Greedy Search（贪心搜索）
在当前阶段优先选择看起来更好的扩展方案；通常比完全枚举便宜，但可能错过全局更优方案。

### 46. Dynamic Programming（动态规划）
保存子问题最优或较优结果以减少重复搜索的算法思想；不同数据库优化器使用方式不同。

### 47. Pruning（剪枝）
提前舍弃不值得继续搜索的候选计划，控制优化器自身的运行开销。

### 48. Hypergraph Optimizer（超图优化器）
MySQL 中另一条查询优化路径，使用超图形式描述连接关系并搜索计划。原文的 MySQL 8.4.6 实验主线使用传统优化器，不能把两个分支混成一条调用链。

### 49. `JOIN::optimize()`（MySQL JOIN 优化入口）
MySQL 查询优化的重要源码函数，负责相关优化工作并进入相应优化分支。注意：这里 `JOIN` 是 MySQL 内部类名，不表示 SQL 一定写了 JOIN。

### 50. `best_access_path()`（评估访问方式）
传统优化器相关函数，用于比较特定连接前缀下表的候选访问方式；不是一个独立运行 SQL 的执行器。

## 五、扫描、连接、聚合和内存

### 51. Table Scan / Full Table Scan（表扫描 / 全表扫描）
顺序访问表记录以寻找符合条件的行。全表扫描不一定慢：匹配比例很高时可能优于大量索引回表。

### 52. Index Scan / Index Lookup（索引扫描 / 索引查找）
利用索引定位或遍历记录。**例子**：`WHERE id=10` 可能使用主键索引查找。

### 53. Range Scan（范围扫描）
按索引读取一段连续键范围。**例子**：`WHERE age BETWEEN 20 AND 30`。

### 54. Covering Index（覆盖索引）
查询需要的列都可从某个索引获取，减少额外读取完整记录的机会。是否覆盖要看查询列和索引结构。

### 55. Table Lookup / Bookmark Lookup（回表）
从二级索引找到记录定位信息后，再访问主表/聚簇索引取未包含的列。InnoDB 中常见的是经二级索引再查聚簇索引。

### 56. Nested Loop Join（嵌套循环连接）
取外侧一行，再从内侧查找匹配行，循环进行。内侧若能使用索引，通常比朴素双重全表循环高效。

### 57. Outer / Inner Input（外侧输入 / 内侧输入）
Nested Loop 中外侧驱动内侧。**注意**：这里的 outer/inner 是算法输入角色，不等于 SQL 的 OUTER JOIN/INNER JOIN 类型。

### 58. Hash Join（哈希连接）
通常先对一侧构建哈希表（Build），再扫描另一侧查找匹配（Probe），常用于等值连接。

### 59. Build / Probe（构建 / 探测）
Hash Join 两个主要阶段：把一侧连接键放入哈希结构，再用另一侧的键查找匹配。

### 60. Merge Join（归并连接）
利用两侧按连接键排序的输入逐步匹配。PostgreSQL 支持；不要默认 MySQL 8.4 具有相同的通用实现。

### 61. Hash Aggregate（哈希聚合）
按分组键维护哈希表并累计 COUNT、SUM 等值。组很多时会占用较多内存。

### 62. Sort / Filesort（排序 / MySQL 排序操作）
为 ORDER BY 等需求建立顺序。MySQL 的 `filesort` 是内部排序方法名称，不表示必然写磁盘文件。

### 63. Materialization（物化）
把中间结果实际保存下来，供后续算子读取或复用；可能涉及内存或临时磁盘空间。

### 64. Temporary Table（临时表）
执行查询过程中保存中间数据的表结构；与业务自己创建的永久表不同。

### 65. Blocking Operator（阻塞算子）
必须先读取相当一部分输入才能产生输出的算子。**例子**：一般排序要先收集输入；Hash Join 构建侧通常先完成哈希表。

## 六、执行器、迭代器和存储引擎

### 66. Executor / Execution Engine（执行器 / 查询执行引擎）
真正运行选定物理计划、调用算子、获取数据并产生结果的组件。

### 67. Volcano Iterator Model（火山迭代器模型）
典型的拉取式算子模型：父节点向子节点请求下一行。教材常写 `open()/next()/close()`；MySQL 具体接口应看 `Init()/Read()` 等实现。

### 68. Pull-Based Execution（拉取式执行）
下游需要数据时向上游请求。**例子**：根节点调用子节点 `Read()`，子节点再调用自己的子节点。

### 69. `Init()` / `Read()`（初始化 / 读取下一行）
MySQL RowIterator 的核心操作。`Init()` 可能执行实际工作；`Read()` 也可能触发多次底层访问。不要把每次 Read 等同于一次磁盘 I/O。

### 70. EOF — End of File / End of Input（输入结束）
迭代器已无下一行。在原文所述的 `ExecuteIteratorQuery()` 相关约定中，`Read()` 返回 0 为得到一行，负数为结束，正数为错误；不能把这个返回约定套给所有函数。

### 71. `ExecuteIteratorQuery()`（驱动迭代器执行查询）
MySQL 执行查询的重要函数，调用根迭代器 `Init()`，反复 `Read()`，并向客户端发送结果。

### 72. `NestedLoopIterator::Read()`（嵌套循环算子读取）
外侧取行、重新初始化内侧、从内侧读取匹配行的核心逻辑。其循环次数是理解 JOIN 性能的关键。

### 73. Handler API（存储引擎接口）
MySQL Server 层访问底层存储引擎的一组抽象接口。使上层执行器无需直接操纵 InnoDB 页面。

### 74. `handler::ha_rnd_next()`（读取下一条扫描记录）
Server 层表扫描常用接口之一，进一步调用具体存储引擎实现。

### 75. `handler::ha_index_read_map()`（按索引键定位记录）
通过索引键及匹配方式定位记录的接口，常用于索引查找路径。

### 76. `ha_index_next_same()`（继续读取相同键的记录）
在已定位某个索引键后，继续读取具有相同键值的后续记录。

### 77. InnoDB（MySQL 事务型存储引擎）
负责索引、页面、缓冲池、事务和记录可见性等底层工作。它不是 SQL 解析器或整个 MySQL Server。

### 78. `row_search_mvcc()`（InnoDB MVCC 行搜索实现）
InnoDB 某些记录读取路径中的核心函数，涉及索引查找与可见性判断；并非所有操作都走完全相同路径。

### 79. MVCC — Multi-Version Concurrency Control（多版本并发控制）
通过记录版本和事务可见性规则，让读写并发时查询看到符合隔离级别的数据。不是简单“每次 SELECT 都读取最新值”。

### 80. Buffer Pool（缓冲池）
InnoDB 缓存数据页和索引页的内存区域。读取一行可能直接命中内存，并不必然访问物理磁盘。

### 81. I/O — Input/Output（输入输出）
此处通常指存储读写；需要区分逻辑页访问、缓存命中与真正的物理磁盘 I/O。

### 82. Vectorized Execution（向量化执行）
一次处理一批行或列值，而非每次只处理一行；有助于减少解释和函数调用开销。DuckDB 等分析型数据库常用。

### 83. SIMD — Single Instruction, Multiple Data（单指令多数据）
CPU 一条向量指令同时处理多个数据元素。向量化执行可利用 SIMD，但两者不是同义词。

### 84. Pipeline Execution（流水线执行）
多个算子尽量连续传递数据，减少中间结果物化；遇到排序、聚合等阻塞操作时可能形成流水线边界。

### 85. OLTP / OLAP（联机事务处理 / 联机分析处理）
OLTP 偏订单、支付、用户更新等短事务；OLAP 偏大量扫描、分组统计、报表。实际系统可能混合两类负载。

## 七、源码验证、日志与实验术语

### 86. `EXPLAIN`（查看估算执行计划）
展示数据库准备采用的访问方式、连接顺序等。**不是**完整的候选方案搜索历史。

### 87. `EXPLAIN ANALYZE`（实际执行并分析）
实际运行查询，显示节点实际行数、循环和耗时等。要避免在生产环境对高成本或有副作用的语句随意使用。

### 88. `optimizer_trace`（MySQL 优化器跟踪）
记录优化器部分决策过程的结构化诊断机制，可观察候选路径、成本与选择原因。需要在同一会话开启并及时读取。

### 89. `INFORMATION_SCHEMA.OPTIMIZER_TRACE`（优化器跟踪结果视图）
读取本会话 optimizer_trace 的位置；与 MySQL error log 或 general log 不是同一个输出渠道。

### 90. DBUG（MySQL 原生调试机制）
Debug 构建中通过既有调试宏/控制串输出函数进入退出及指定调试内容；**只能覆盖有埋点的位置**。

### 91. `DBUG_TRACE` / `DBUG_PRINT`（调试跟踪 / 调试输出）
源码中的调试设施；前者常用于跟踪函数进入退出，后者输出指定调试信息。没有宏的函数不会凭空出现完整跟踪。

### 92. GDB — GNU Debugger（GNU 调试器）
调试本地程序、设置断点、查看调用栈和变量的工具。用于 MySQL Debug 构建时可验证真实运行路径。

### 93. Breakpoint / Backtrace（断点 / 调用栈回溯）
断点让程序停在指定位置；`bt` 查看当前线程如何一层层调用到这里。**注意**：调用栈只反映停下来的瞬间。

### 94. Instrumentation（埋点）
在源码中记录时间、计数或事件。**例子**：统计某个迭代器 `Read()` 成功多少次。埋点本身会影响性能。

### 95. Profiler / TimingIterator（性能计数器 / 计时迭代器）
记录算子耗时、循环和输出行数的工具或包装器。不同节点可能使用不同计数实现。

### 96. Loops（节点执行循环次数）
`EXPLAIN ANALYZE` 中常见指标，尤其要看 Nested Loop 内侧被反复初始化或执行的次数；不要误当作整个查询只运行了多少次。

### 97. Performance Schema（MySQL 性能监控架构）
MySQL 的语句、阶段、等待等性能指标采集体系，可辅助诊断，但不等于优化器全部搜索轨迹。

### 98. General Log / Slow Query Log / Error Log（通用查询日志 / 慢查询日志 / 错误日志）
分别侧重请求记录、慢 SQL 与服务器诊断；都不能直接代替 optimizer_trace。

### 99. Debug Build / Release Build（调试构建 / 发布构建）
Debug 便于断点与 DBUG，Release 更适合性能测量；不应把带大量日志的 Debug 时延直接与 Release 公平比较。

### 100. Git SHA / Commit / Tag（提交哈希 / 提交 / 标签）
用确定的源码版本复现实验。Tag 是命名引用，Commit SHA 精确定位某次提交；源码行号可能随版本变化。

### 101. Git Submodule / Gitlink（子模块 / 子模块提交引用）
主仓库固定引用另一仓库的某次提交，用于锁定 MySQL 上游源码版本；不是直接把所有源码复制进主仓库。

### 102. GitHub Actions / CI（GitHub 自动化工作流 / 持续集成）
自动编译、运行测试、采集日志和保存产物的环境。原文拟在 CI 构建 MySQL Debug 实例，而非本地编译。

### 103. Oracle / Ground Truth（正确性基准 / 真实参照结果）
这里的 oracle 是用于校验查询结果的独立正确答案，**不是 Oracle 数据库产品**。例如用独立 Python 程序计算应有的分组总数。

### 104. Reproducibility（可复现性）
别人能按固定源码、数据、SQL、配置和脚本重现相同结论；需记录索引、统计状态、运行环境与日志。

## 八、四组容易混淆的概念

| 容易混淆 | 正确区分 | CRUD 开发类比 |
|---|---|---|
| AST vs 执行计划 | AST 表示 SQL 写了什么；计划表示如何执行 | Controller 接收到的请求结构 vs Service 处理方案 |
| Logical Plan vs Physical Plan | 逻辑算子 vs 具体扫描/连接算法 | 业务步骤 vs 具体 SQL/索引实现 |
| AccessPath vs RowIterator | 物理计划描述 vs 实际执行对象 | 配置/任务定义 vs 正在运行的对象 |
| Estimated Rows vs Actual Rows | 优化前估算 vs 执行时测量 | 预计 1 万条 vs 真正读出 30 万条 |
| Cost vs Duration | 内部相对成本单位 vs 实际耗时 | 工时估算分值 vs 秒表时间 |
| JOIN Order vs JOIN Algorithm | 先连哪张表 vs 用哪种算法连接 | 先处理哪个接口 vs 采用什么处理实现 |
| Outer Input vs OUTER JOIN | 算法驱动侧 vs SQL 连接语义 | 迭代器角色 vs 查询语义 |
| `Read()` vs Disk Read | 迭代器取下一行 vs 物理磁盘读 | 调一次 DAO 方法不等于发生一次磁盘 I/O |
| optimizer_trace vs EXPLAIN ANALYZE | 解释选择原因 vs 测量实际执行 | 为什么选此方案 vs 方案跑得怎样 |
| DBUG vs GDB | 预埋日志机制 vs 交互式调试器 | 打日志 vs 断点调试 |

## 九、从源码入手的最短学习路径（按原文方案）

**第 1 步：只看一条简单 SELECT。** 先用 `EXPLAIN FORMAT=TREE` 看计划，再用 `EXPLAIN ANALYZE` 看真实行数；认识 Scan、Filter、Index Lookup。

**第 2 步：阅读解析和准备。** 找 `dispatch_command()`、`dispatch_sql_command()`、`Sql_cmd_dml::prepare()`、`Query_block::prepare()`；回答“SQL 怎样变成可优化的结构”。

**第 3 步：阅读优化器。** 找 `JOIN::optimize()`、`JOIN::make_join_plan()`、`best_access_path()`；打开 `optimizer_trace`，回答“为什么用这个索引/这个 JOIN 顺序”。

**第 4 步：阅读计划实例化。** 找 `JOIN::create_access_paths()`、`CreateIteratorFromAccessPath()`；回答“计划如何变成执行对象”。

**第 5 步：阅读执行器。** 找 `ExecuteIteratorQuery()`、`NestedLoopIterator::Read()`；记录根节点 Init/Read 和内侧 loops。

**第 6 步：阅读存储引擎边界。** 找 `TableScanIterator::Read()`、`handler::ha_rnd_next()`、`handler::ha_index_read_map()`、InnoDB `row_search_mvcc()`；回答“数据究竟从哪里来”。

**第 7 步：形成三证合一报告。** 源码说明调用机制；`optimizer_trace` 说明优化选择；`EXPLAIN ANALYZE` 说明真实执行。必要时用 Debug DBUG/GDB 补充调用栈。不要把不同次运行的日志拼成一次调用时序。

## 十、面试时可直接复述的回答

**问：执行计划如何生成？** SQL 先被解析和语义准备，再由优化器根据统计信息、候选访问路径、JOIN 顺序和成本估算选择物理计划。MySQL 8.4 的相关执行计划可用 AccessPath 树表示，再构造 RowIterator 对象。

**问：执行计划如何执行？** 执行器从根迭代器开始 `Init()`，反复 `Read()`；父节点向子节点拉取记录，扫描和索引迭代器通过 handler 接口访问 InnoDB，最终返回结果。部分算子会阻塞并预先消耗输入。

**问：怎样从源码证明？** 固定 MySQL 源码版本，阅读 Parser→Optimizer→AccessPath→RowIterator→handler 的调用链，用 optimizer_trace 观察优化决策，用 EXPLAIN ANALYZE 观察实际执行，用 DBUG/GDB 补充真实调用证据。
